# Genesis VRF-key / Bitcoin-entropy ceremony ordering

Date: 2026-08-18  
Classification: **GRINDING FINDING**  
Production changes: none.

## Critical result

The specification recognizes the exact risk—validator VRF keys must be finalized
before the Bitcoin seed becomes known—but the production ceremony tooling does
not enforce or produce evidence of that ordering. `indra-genesis create-vrf-proof`
can be run at any time, and `indra-genesis build` accepts validator keys, stake,
PoPs, the already-known Bitcoin header, and its confirmation depth together.
The governing snapshot is constructed only after that final manifest is loaded.

A deterministic audit reproducer generated valid candidate VRF keypairs and
valid genesis PoPs *after* fixing a known Bitcoin-derived seed. It recomputed the
complete real snapshot root for every key before constructing the production
`INDRA-PROPOSER-SORTITION-v2` transcript. Selection measurably improved the
validator's height-1 schedule. This triggers the requested stop condition. No
remediation was attempted.

## 1. Actual ordering and mutability

### What the specification intends

The descriptor is supposed to be published for a future height before validator
VRF keys are finalized. The spec explicitly says the ordering prevents validators
from grinding keys after learning the seed
([`docs/PROPOSER_AUTHORIZATION_VRF_DESIGN_SPEC.md:609`](../../docs/PROPOSER_AUTHORIZATION_VRF_DESIGN_SPEC.md#L609),
[`docs/PROPOSER_AUTHORIZATION_VRF_DESIGN_SPEC.md:645`](../../docs/PROPOSER_AUTHORIZATION_VRF_DESIGN_SPEC.md#L645)).
It does not define a machine-verifiable VRF-key-finalization artifact, deadline,
or minimum distance between that finalization and the Bitcoin target.

### What the tools actually enforce

1. Validator identity/hybrid/VRF material is generated by wallet/key tooling
   independently of a genesis ceremony state machine.
2. `indra-genesis create-vrf-proof` loads the current hot-key file, derives its
   VRF key, and creates a PoP for `(chain_id, validator_id, vrf_pk, epoch=0)`
   ([`indra-cli/src/bin/genesis.rs:34`](../../indra-cli/src/bin/genesis.rs#L34)).
   It accepts no descriptor, target height, commitment, or cutoff evidence.
3. `indra-genesis build` receives the Bitcoin network, height, **header**, depth,
   every validator's public metadata/cold file/VRF proof, and stake in one command
   ([`indra-cli/src/bin/genesis.rs:79`](../../indra-cli/src/bin/genesis.rs#L79)).
4. Only then does it verify the header is the active-chain block and has the
   requested confirmations ([`indra-cli/src/bin/genesis.rs:180`](../../indra-cli/src/bin/genesis.rs#L180)).
5. Manifest validation verifies each VRF PoP against the submitted key
   ([`indra-node/src/genesis.rs:244`](../../indra-node/src/genesis.rs#L244)). A
   freshly generated post-seed key therefore passes; PoP proves possession, not
   pre-seed commitment.
6. Node genesis loading installs validator IDs, vote keys, VRF keys and stakes
   from the final manifest ([`indra-node/src/genesis.rs:570`](../../indra-node/src/genesis.rs#L570)).
7. The genesis consensus snapshot is constructed from the resulting active
   registry, then canonically sorted by validator ID
   ([`indra-state/src/chain.rs:629`](../../indra-state/src/chain.rs#L629)).

| Stage | Values still mutable under current tooling |
|---|---|
| Descriptor selection/publication | There is no enforced publication artifact; all descriptor and validator fields remain mutable. |
| Validator identity/key generation | Validator ID, Ed25519/ML-DSA voting keys, VRF key, cold keys remain replaceable. |
| VRF PoP generation | Another key and corresponding valid PoP can be generated without reference to the Bitcoin event. |
| Target block revealed | All validator entries, stake and membership still remain CLI inputs. |
| 100+ confirmations | Same; build has not yet fixed a manifest or snapshot. |
| Final build | Header, validator list, stakes and key files are combined; only the emitted manifest/fingerprint fixes them. |
| Node genesis load/finalization | Snapshot/root, state root, seed and fingerprint become deterministic and immutable for that published chain. |

There is no separate on-disk “validator material frozen” state between descriptor
publication and target revelation.

## 2. Preserved key-grinding reproducer

Files:

- `key_grinding_reproducer/Cargo.toml`
- `key_grinding_reproducer/src/main.rs`
- `key_grinding_reproducer/output.txt`

Rerun:

```bash
cargo run --release --manifest-path \
  audit_evidence/18_bitcoin_genesis_entropy/key_grinding_reproducer/Cargo.toml
```

Fixture:

- fixed chain ID and deterministic 80-byte simulated known Bitcoin header;
- genesis seed derived by production `derive_genesis_election_seed`;
- four validators with equal 100,000,000,000-Spark stake;
- mainnet `f=3/8` (`F=6917529027641081856`);
- target validator stake fraction `1/4`;
- fixed hybrid identities/vote keys and three fixed peer VRF keys;
- candidate target-validator VRF seeds derived deterministically by index;
- each candidate generates and verifies a genuine production genesis PoP;
- each candidate is inserted into a new `ConsensusSnapshot::new`, which validates
  entries and recomputes the snapshot root;
- height 1, rounds 0–31 use production `proposer_vrf_alpha` and `vrf_prove`;
- eligibility uses the exact production Q768 threshold. The threshold is computed
  once because `F`, `w`, and `W` are identical for all candidates; only the real
  alpha and VRF output vary with the recomputed root.

The ideal per-key, per-round eligibility probability is:

```text
p = 1 - (1 - 3/8)^(1/4)
  = 0.1108602949805385993872894024036575776...
```

For independent candidate keys, probability of at least one round-0-eligible key
is `1-(1-p)^N`: 20.94% at 2 keys, 84.7412109375% at 16, and effectively 1 at
256/4096.

Observed deterministic nested corpus:

| candidates searched | selected first eligible round | eligible rounds among 0–31 | selected snapshot root prefix | selected first-round priority prefix |
|---:|---:|---:|---|---|
| 2 | 2 | 4 | `3410a98f6f71cc57` | `128d04061dcc8edf` |
| 16 | 0 | 5 | `fc9cc62a8a106b10` | `567e34a3fb09e7b3` |
| 256 | 0 | 3 | `8199fdf31b9e0fc5` | `0e8c6e467e7774f3` |
| 4096 | 0 | 2 | `f1f752c2a04e80c6` | `00178510bce01aa9` |

The count column is not the primary optimization after round 0 is reached: the
reproducer then minimizes the full 512-bit production priority. The improvement
from priority prefix `56...` at 16 candidates to `00...` at 4096 demonstrates a
second selection axis even when round-0 eligibility is already obtained.

## 3. Snapshot-root interaction

The experiment does not hold the root constant. A snapshot entry commits
validator ID, weight, Ed25519 key, ML-DSA key, VRF key, suite and activation epoch
([`indra-core/src/types/consensus_snapshot.rs:22`](../../indra-core/src/types/consensus_snapshot.rs#L22)).
The root commits the canonical entry list, total weight, `F`, and Q768 certificate
([`indra-core/src/types/consensus_snapshot.rs:310`](../../indra-core/src/types/consensus_snapshot.rs#L310)).
Production alpha then binds chain ID, seed, height, round, snapshot root and
proposer ID ([`indra-core/src/types/proposal.rs:34`](../../indra-core/src/types/proposal.rs#L34)).

Accordingly each candidate changes both its public key and its alpha through a
new root. The attack remains valid under that feedback.

## 4. Miner-side information after validator material is fixed

If the complete validator snapshot is public before the target height, a miner
can compute, for every candidate valid header:

1. the candidate external entropy and genesis seed;
2. the already-known snapshot root;
3. every public alpha `(chain, seed, height, round, root, validator_id)`.

The miner cannot compute an honest validator's VRF output from its public key.
It can evaluate outcomes for any validator whose VRF secret it controls or whose
operator colludes/replies during mining. It can also grind directly on any public
predicate of the seed. Thus public pre-fixing closes validator post-seed key
selection but exposes targeted seed evaluation to miners/coalitions, bounded by
the Phase-9 discard/reorg economics.

## 5. Commitment alternatives (security-property analysis only)

No design is implemented here.

- **A — VRF keys fixed and public before target:** binding is straightforward and
  prevents validator key selection. It provides no hiding from a miner colluding
  with those key holders and reveals the full snapshot input before mining.
- **B — binding/hiding commitment before target, reveal afterward:** a canonical
  commitment such as `H(domain || validator_id || vrf_pk || nonce)` can bind a
  key while hiding it, assuming collision/preimage resistance and an unpredictable
  nonce. Reveal plus the existing VRF PoP proves the committed key is controlled.
  This can simultaneously prevent post-seed key choice and prevent an unaided
  miner from knowing the VRF key during target mining. It is insufficient if only
  the VRF key is committed, because other snapshot fields remain grindable.
- **C — full consensus material committed before target:** strongest binding if
  it covers the canonical validator set, identities, vote/VRF keys, weights,
  suite/activation data and all other snapshot inputs. If published in the clear,
  it has A's miner-information tradeoff; a binding/hiding commitment to the full
  material avoids that at the cost of a reveal/availability ceremony.

Option B requires canonical field framing, a domain/version tag, nonce entropy,
an immutable public publication time, one commitment per admitted validator, and
an all-or-abort reveal rule. The commitment set itself must be fixed; otherwise
operators can select which commitments to include after seeing the seed.

## 6. Other grindable genesis material

Changing any of the following after target revelation changes the snapshot root
and therefore every proposer alpha:

- self-stake/consensus weight;
- validator membership or identity;
- Ed25519 or ML-DSA vote key;
- VRF key;
- suite or activation epoch.

Manifest array ordering is not a lever because production sorts snapshot entries
by validator ID before root construction. Changing validator IDs changes both
that canonical order and the committed entry bytes. Cold keys and liquid genesis
UTXOs affect the broader state/fingerprint; they are not snapshot-entry fields,
but leaving them mutable still permits selection among different genesis chain
identities. A sound entropy ceremony therefore needs a pre-target commitment to
the complete consensus-critical genesis validator material, not merely individual
VRF keys.

## 7. Final disposition

**GRINDING FINDING.** The intended ordering is described but not cryptographically
or operationally enforced by the repository workflow. A validator able to choose
its VRF key after learning Bitcoin entropy can measurably optimize immediate
proposer eligibility and priority, even when the snapshot root is correctly
recomputed. The reproducer is preserved. Per the task's stop rule, this phase
does not remediate the ceremony.
