# Signed DNS Node Discovery

INDRA’s DNS seeds are a discovery cache, not consensus state. The source of
truth remains the on-chain validator set and each validator’s on-chain
`network_addr`. DNS is only a convenient bootstrap transport.

This repository now supports an EIP-1459-style signed DNS discovery overlay:
clients can verify a DNS-published node list against an ML-DSA-87 public key
known independently of DNS. This means a compromised DNS provider account can
at most hide or stale the discovery list; it cannot forge a valid replacement
list unless the separate signing key is also compromised.

## Why not Ethereum’s exact format?

Ethereum EIP-1459 signs the root record with secp256k1. INDRA deliberately does
not copy that signature primitive because discovery should not become a
classical-only weak link in an otherwise post-quantum-oriented stack.

INDRA uses ML-DSA-87 for the discovery signature. An ML-DSA-87 signature is much
larger than a secp256k1 signature, so it is not embedded directly in one root
TXT record. Instead:

- the root TXT record contains a sequence number, a hash of the canonical node
  payload, a node-chunk count, a hash of the ML-DSA signature, and a
  signature-chunk count;
- node-list chunks are published as hash-addressed TXT records;
- signature chunks are published as hash-addressed TXT records;
- the verifier reassembles both payloads, checks the hashes, and verifies the
  ML-DSA signature over the canonical root fields.

The DNS provider therefore remains a transport/cache layer. The trust anchor is
the configured ML-DSA public key.

## Record shape

Root TXT content:

```text
indradisc-root:v1 seq=<n> nodes=<sha256-node-payload> nodes_chunks=<n> sig=<sha256-signature> sig_chunks=<n>
```

Chunk TXT records use relative names generated by the node code:

```text
_indra-seed-nodes-<index>-<hash-prefix>.<seed-host>
_indra-seed-sig-<index>-<hash-prefix>.<seed-host>
```

The canonical node payload is a sorted, deduplicated newline-separated list of
socket addresses such as:

```text
116.203.185.28:30303
5.161.221.10:30303
```

## Configuration

Signed discovery is controlled separately from DNSSEC validation:

```toml
[network]
dns_seed_validation = "warn"          # DNSSEC A-record validation
dns_seed_signed_validation = "off"    # off | warn | require
# dns_seed_signed_public_key = "<ML-DSA-87 public key hex>"
```

- `off`: do not attempt signed-list discovery.
- `warn`: prefer a valid signed list when a public key is configured, but fall
  back to the existing DNSSEC A-record path if the signed list is unavailable or
  invalid.
- `require`: accept only a valid signed list from DNS seeds. This rejects DNS
  seed discovery for that cycle if the signed list is absent or invalid, but it
  does not block node startup; bootstrap peers, persisted peers, PEX, genesis
  hints, and on-chain validator addresses still work.

## Publishing

`ops/dns_publish_seed_records.py` can publish both existing A records and signed
TXT records. It keeps Cloudflare credentials separate from signing credentials:
the Python publisher invokes an explicit signer command, and refuses
`--signed` publishing without one.

Example dry run:

```bash
ops/dns_publish_seed_records.py \
  --zone-id "$CLOUDFLARE_ZONE_ID" \
  --token-file /path/to/cloudflare.token \
  --signed \
  --signed-seq 1 \
  --signer-command "target/release/dns_seed_sign --pq-seed-file /path/to/dns-seed-signing.seed"
```

The signing seed file must be `0600` or stricter on Unix systems. The signing
key should be independent of validator identity keys and independent of DNS
provider credentials. Treat it like other high-value operational key material:
store it encrypted at rest or behind a platform/ops secret manager, expose it
only to the signing wrapper, and rotate deliberately if compromised.

## Coexistence and rollout

Plain A records remain supported for transition and emergency fallback. The
recommended rollout order is:

1. generate and protect the independent ML-DSA discovery signing key;
2. configure/publish the public key in node config for test deployments;
3. publish signed TXT records in dry-run, then apply;
4. run nodes with `dns_seed_signed_validation = "warn"` and confirm logs show
   verified signed peers;
5. only after operational confidence, consider `require`.

DNSSEC remains useful even with signed discovery: it authenticates the DNS
transport and prevents trivial DNS tampering. Signed discovery adds a second,
DNS-operator-independent integrity layer over the node list itself.
