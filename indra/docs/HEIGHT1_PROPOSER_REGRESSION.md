# INDRA Height-1 Proposer Regression Diagnostic

## Executive Summary

The height-1 `WrongProposer` regression was caused by an inconsistent proposer
self-check: `NodeEngine::is_proposer()` decided local eligibility by validator
ID alone, then injected the local VRF output into that validator's candidate
entry without first checking that the local VRF public key matched the VRF key
registered in the active validator set. `produce_block()` performs the stricter
check and looks up the proposer by VRF public key, so a node with a mismatched
local `vrf_seed` versus genesis `vrf_pk` could believe it should propose and
then fail immediately with `ConsensusError::WrongProposer`.

## Step 1 — Exact Failure Point

The failing `WrongProposer` branch is the first check in
`indra-consensus/src/producer.rs::produce_block`:

```rust
election
    .candidates
    .iter()
    .find(|candidate| candidate.vrf_pubkey == template.proposer_vrf_keypair.public_key())
    .map(|candidate| candidate.validator_id)
    .ok_or(ConsensusError::WrongProposer)?
```

This branch fires when the local proposal keypair's public VRF key is absent
from the election candidate list. The new regression test
`is_proposer_rejects_registered_vrf_key_mismatch` reproduces the pre-fix shape:
a node's validator ID is present in the active set, but its registered
`vrf_pk` does not match its local `vrf_seed`.

## Step 2 — Diff Analysis

Commit `314b273` did not change `produce_block()`. The regression surfaced in
the caller path because proposal eligibility and proposal construction were
using different notions of local proposer identity:

- `is_proposer()` used the local `validator_id` and local VRF output.
- `produce_block()` required the local VRF public key to match an election
  candidate's registered `vrf_pubkey`.
- `propose()` reconstructed a VRF keypair from `config.vrf_seed` instead of
  using the already-loaded engine keypair.

The stale-QC fix changed proposal gating/timing, but the underlying proposer
identity bug was already present: local eligibility could be true even when
the active-set VRF key did not match the local signing key.

## Step 3 — Height-1 Special Case

Height 1 correctly does not require a previous QC. The new
`last_qc_is_stale()` path also correctly returns `false` at state height 0, so
the stale-QC recovery logic is not the direct cause of height-1 failure.

The actual height-1 edge was that this is the first time a wiped node proves
its local VRF key against the genesis active-set `vrf_pk`. If those keys are
inconsistent, the node fails before it can produce the first block.

## Step 4 — VRF/Candidate Construction Path

Election candidates are built from:

```rust
state.validators.active_validators().filter_map(|v| v.vrf_pk ...)
```

The local proposal key is loaded from node key material. Before this fix,
`is_proposer()` did not compare those two public keys. After this fix:

- `is_proposer()` refuses to return true unless the local validator's
  registered candidate `vrf_pubkey` equals the local VRF keypair public key.
- `propose()` uses the already-loaded `self.vrf_keypair` instead of
  reconstructing a separate keypair from `self.config.vrf_seed`.

## Fix Implemented

1. Added a registered/local VRF public-key equality check in
   `NodeEngine::is_proposer()`.
2. Changed `NodeEngine::propose()` to use the already-loaded local VRF keypair.
3. Added `Clone` for `VrfKeypair` so the block template can receive the loaded
   keypair without reconstructing it from config.
4. Added regression coverage:
   - `fresh_genesis_height_one_block_production_succeeds`
   - `is_proposer_rejects_registered_vrf_key_mismatch`

## Operational Note

If a deployed genesis file still contains VRF public keys generated by an older
key derivation algorithm, validators must regenerate matching key/genesis
material before redeploy. The node will now refuse to self-elect with a
mismatched registered/local VRF key instead of repeatedly attempting invalid
proposals.
